🎵 Singlish：一个 vibe coding 出来的「听歌背单词」应用

每个雅思单词都藏在一段流行歌里：Apple Music 官方试听 + 卡拉 OK 同步歌词。从公版儿歌到 YouTube 再到 Apple 试听，推倒重来三次的 vibe coding 实录

🤔 起因#

背雅思单词这件事，最大的问题不是"记不住"，而是无聊。单词书里的例句读到第三遍，人就已经走神了。

但歌词不一样。一句你单曲循环过一百遍的歌词，里面的单词想忘都忘不掉。所以这个项目只有一个想法：让每个雅思单词都住在一首真实的流行歌里，点一下，就听到歌手把这个词唱出来。

它叫 Singlish。字面意思是 Sing + English，边唱边学英语。它还有一层意思：在新加坡，Singlish 指的是新加坡人说的那种英语，句尾带个 lah 的那种。一个名字两种读法，我觉得挺合适：学英语本来就不必一板一眼。

这篇文章替换了之前介绍 SingTheWord 的旧文。Singlish 是同一个想法的重做版：换了音源、换了选词方式，也换了一整套设计。

🎧 它长什么样#

在线体验： https://bigjeager.github.io/singlish/ 源码： github.com/bigjeager/singlish

（截图里除目标词以外的歌词做了模糊处理，出于版权考虑。实际页面上歌词是完整显示的。）

🎤 它能干什么#

  • 100 个雅思词，出自 89 首流行歌、69 位歌手：Coldplay、Adele、Billie Eilish、Bruno Mars……还有我点名要多放的 The Weeknd（7 个词）和 Imagine Dragons（8 个词）；
  • 官方原声，没有广告：播放的是 Apple Music 的 30 秒官方试听，只截唱到这个词的那十几秒；
  • 卡拉 OK 式歌词：当前行放大，粉到橙的渐变随歌声逐词扫过，唱到目标词时，黄色荧光笔"啪"地弹一下；
  • 像音乐 App 一样用：桌面端点卡片就唱，手机端左右滑动，滑到哪张唱哪张；默认一首接一首连着播，还有随机和单曲循环；
  • 单词卡本身：英式音标（点一下会朗读）、中英释义、雅思常用搭配、雅思分段标签，以及"歌里唱的是 amazing，它是 amaze 的形容词"这类词形说明；
  • 氛围：整个页面的背景是当前歌曲封面的模糊光晕，换一首歌，页面就换一种颜色；正在播放的封面是一张转动的 CD；
  • 纯静态：一个 index.html，托管在 GitHub Pages，没有后端。

🛤️ 过程：推倒重来了三次#

整个项目是我和 AI（Claude Code）结对 vibe 出来的。回头看，写代码占的时间很少，大部分时间花在被现实约束推着换方案上。

第一版：公版歌曲 + 浏览器合成旋律#

一开始最担心的是版权：流行歌的录音和歌词都不能随便放进网页。于是 AI 给了一个很"工程师"的方案：只用公有领域的歌（传统民歌、赞美诗、1929 年前的老歌），旋律按乐谱用 Web Audio 实时合成。好处是高亮和音符能逐音节严格同步，完全离线也能用。

数据是拆给 4 个子 agent 并行写的。结果有两组被拦了下来，重试也一样：让 AI 大段写出知名歌曲的歌词原文，会触发安全策略，公版的也不例外。最后一半词条只好用"原创歌词 + 公版曲调"补齐。

效果能用，但我看了一眼就说：不要儿歌，要流行音乐。 八音盒版的 Twinkle Twinkle，谁会想边听边背单词？

第二版：YouTube + 流行歌#

换流行歌以后，思路也反过来了，这是整个项目最关键的一次转向：不是"给单词找歌"，而是"从歌里找单词"。

  1. 列了约 350 首流行歌；
  2. 从 LRCLIB 拉取带逐行时间轴的歌词；
  3. 用一份约 900 词的雅思词表去扫，词形变化也算（achieved、achieving 都能对上 achieve）；
  4. 结果在这些歌里找到了 302 个雅思词，挑出 100 个，每首歌一个词；
  5. 再给每首歌找一个 YouTube 视频，要求视频时长和歌词时间轴对得上，保证跳到第几秒就是唱那一句。

这一版的设计也被我打回过一次。第一稿是浅色、衬线字体的"歌词本"风格，我的评价是太正式了。第二稿就是现在这套深色音乐 App 风格：封面光晕背景、唱片套一样的卡片、会跳的均衡器、粉橙渐变的卡拉 OK。

然后问题来了：YouTube 的广告太多。为了视频稳定，我还特意把视频源都换成了官方频道（100 个里有 92 个是官方的），结果官方视频恰恰是插广告最多的。嵌入播放器里的广告，网页是关不掉的。

另外还有个小坑：直接双击打开 HTML，YouTube 会报 Video player configuration error（错误 153）。YouTube 现在要求嵌入页面必须有正常的 http(s) 地址，file:// 不行。

第三版：Apple Music 官方试听#

没有广告、官方授权、国内一般也能访问的音源，就是 Apple Music 的 30 秒试听。但它有个大问题：**苹果不告诉你这 30 秒是从整首歌第几秒开始截的。**不知道起点，歌词时间轴就对不上。

解法是在本地跑语音识别：

  1. 给每首歌在 iTunes Search API 上找同一首（歌手、歌名、时长都要对上），拿到试听地址；
  2. 下载试听，用 whisper.cpp（small.en 模型，在 Mac 上本地跑）识别出唱了什么；
  3. 把识别出的每一段和整首歌的歌词逐行做模糊匹配，每次匹配投一票"起点 = 歌词时间 − 识别时间"，票数最多的那一簇就是试听的真实起点；
  4. 第一轮有将近三成没对上。原因是 whisper 常把两三句歌词合成一段，和单独一行比对不上。第二轮改用逐词时间戳，拿连续的词去匹配，又救回了 79 首。

最后大约 400 首候选歌里，Apple 上找到 346 首，对齐成功 323 首。

选词也变了：只能从这 30 秒里找。我加了一道校验：目标词不但要出现在试听范围内的歌词里，还必须被 whisper 真的听到。这道校验一举两得，既确认试听里确实唱了这个词，也能挡掉起点算错的歌。30 秒的窗口很窄，原来 900 词的词表不够用，又补了约 460 个雅思常考、歌里也常出现的词，最后在试听片段里找到 184 个词，选出 100 个。

🎨 一堆小改动，都是用出来的#

功能上线后，大部分改动来自"我自己用着别扭"：

  • 按钮上的字太丑：播放条上"随机 / 循环 / 连播"这些文字全部去掉，只留图标，开启状态用粉色图标加淡粉色底表示；
  • “连播"这个开关没人看得懂：一般音乐网站的默认逻辑就是一首接一首播下去，所以删掉开关，改成默认连播；
  • 随机播放：下一首随机挑，优先还没唱过的词；“上一首"按实际听过的顺序往回退；
  • 封面改成 CD：播放时转，暂停时停在当前角度，和首页卡片上的小唱片呼应；
  • 电脑端播放条被挡住：右侧整列限制在一屏以内，歌词区自动填满剩余高度；
  • 歌词溢出：当前行放大 6% 以后，长句右边会被裁掉几像素。修法是所有行都按"100% ÷ 1.06"的宽度换行，放大后刚好填满。然后把 100 个词的每一行都自动检查了一遍。

⚙️ 几个值得记一笔的技术点#

1. 页面里不存一句歌词。 数据文件只存"哪首歌、第几秒、试听起点”，歌词在用户打开页面时实时从 LRCLIB 获取，而且只显示目标词前后几句。音频也是直接从 Apple 的 CDN 播放，仓库里没有一个字节的音乐。

2. 逐词高亮是估算的。 LRC 只有每一行的起止时间，行内每个词的进度按字符长度分配。大多数时候看不出来，偶尔会快半拍。

3. iPhone 的自动播放限制。 iOS 只允许在用户点击的那一刻开始播放音频，滑动不算点击。所以第一次点击时先静音播放一下，把音频"解锁”，之后滑到哪张就能直接播哪张。

4. 用无界面浏览器自测。 截图、播放、滑动、布局是否溢出，都用 Playwright 驱动 Chrome 自动测。有一次我在自己的浏览器里测，页面怎么都不动，查了半天才发现那个标签页被切到了后台，Chrome 把后台页面的脚本限流了。

💭 一点 vibe coding 感受#

AI 负责手速，人负责品味和决策。 这句话在上一版的文章里说过，这次体会更深。三次推倒重来，没有一次是因为代码写不出来，都是因为现实约束：版权、平台策略、广告、苹果不公开的试听起点。每一次换方案，AI 都能很快给出几个可行选项和各自的代价，但选哪个、什么样的体验算"对"，得人来判断。

约束反而逼出了更好的设计。 “从歌里找词"最初是被 30 秒试听窗口逼出来的，结果它恰恰是最自然的学法：你听到的那一句，就是你要记的那个词。

反馈越具体，迭代越快。 “太正式了"“字太丑了"“这个按钮看不懂"这种一句话反馈，AI 基本一轮就能改到位，还会顺手把同类问题一起检查掉。

还没做的：

  • 搜任意单词，立刻生成卡片：离线把几千首歌的试听都对齐、建好"单词 → 歌曲 + 时间点"的索引，查询时只做查表；
  • Apple Music 会员听整首：接入 MusicKit，会员可以直接用整首歌的时间轴，不再受 30 秒限制，也不需要 whisper。
